# Architecture Decisions

This document records the key architectural decisions behind SignalOps. It provides context for the current design and helps keep future changes consistent with the project's engineering principles.

## ADR-001: Hybrid DDD-Style Modular Monolith

**Status:** Accepted

**Decision:**
Structure the backend around domain areas, with dedicated services, repositories, and schemas rather than generic controllers and shared data-access logic.

**Rationale:**
SignalOps has distinct domains such as authentication, users, source applications, ingestion, batches, incidents, and dashboards. A modular monolith keeps these responsibilities separated while avoiding the operational and deployment complexity of distributed services.

---

## ADR-002: Async FastAPI and SQLAlchemy

**Status:** Accepted

**Decision:**
Use FastAPI with asynchronous SQLAlchemy sessions for backend APIs and database operations.

**Rationale:**
The application performs I/O-heavy API and database operations as well as pipeline orchestration. Async I/O provides efficient request handling without adding unnecessary architectural complexity.

---

## ADR-003: Repository Layer for Persistence

**Status:** Accepted

**Decision:**
Keep database access behind repository abstractions rather than querying directly from API routers or higher-level services.

**Rationale:**
Repositories provide a consistent persistence boundary that can be reused across the ingestion and incident pipelines. They also make database operations easier to isolate and test.

---

## ADR-004: Source-Application Parsing Registry

**Status:** Accepted

**Decision:**
Use registries to select parsers and domain rules based on the source application type.

**Rationale:**
Different applications produce different log formats and operational signals. Registry-based dispatch allows application-specific behavior to be added without turning the ingestion pipeline into a collection of large conditional branches.

---

## ADR-005: Hybrid Parsing and AI-Assisted Analysis

**Status:** Accepted

**Decision:**
Use Amazon Bedrock selectively for unresolved log normalization and incident analysis.

**Rationale:**
Predictable formats should be handled deterministically through explicit parsers and rules. AI is introduced where semantic uncertainty or higher-level operational reasoning provides additional value. This keeps the core pipeline predictable while allowing the system to handle unknown formats and generate useful incident analysis.

---

## ADR-006: JWT Access Tokens with Hashed Refresh Tokens

**Status:** Accepted

**Decision:**
Use short-lived JWT access tokens and store refresh tokens only in hashed form.

**Rationale:**
JWTs provide efficient stateless access-token verification, while hashed refresh tokens allow sessions to be revoked without storing reusable credentials. Token versioning further supports session invalidation.

---

## ADR-007: Generated Frontend API Client

**Status:** Accepted

**Decision:**
Generate the frontend API client from the backend's OpenAPI schema.

**Rationale:**
The backend API remains the source of truth for the frontend contract. Generated types and client methods reduce API drift and make interface changes easier to detect during development.

---

## ADR-008: External Environment Configuration

**Status:** Accepted

**Decision:**
Keep backend environment files outside the repository under:

```text
~/.config/signalops/backend/
```

with separate files for development and production environments.

**Rationale:**
Secrets and environment-specific configuration should not be stored in Git. Keeping runtime configuration outside the repository also provides a clear separation between application code and deployment configuration while allowing containerized deployments to consume the same configuration structure.

---

## ADR-009: PostgreSQL as the Primary Persistence Store

**Status:** Accepted

**Decision:**
Use PostgreSQL as the primary persistence layer for application data and intelligence generated by the pipeline.

**Rationale:**
SignalOps stores related entities across users, source applications, batches, raw logs, semantic events, signals, incidents, and AI analyses. PostgreSQL provides transactional consistency and relational querying suitable for these interconnected datasets.

---

## ADR-010: Redis for Rate Limiting

**Status:** Accepted

**Decision:**
Use Redis for request rate limiting rather than persisting rate-limit state in PostgreSQL.

**Rationale:**
Rate limiting requires fast, short-lived counters that are accessed frequently. Redis provides an appropriate in-memory store without adding operational state to the primary application database.
